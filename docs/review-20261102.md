## 一、结论摘要

整体判断：**这是一个"功能已完成度很高、生产鲁棒性还没跟上"的项目**。三个专项的结论方向高度一致：核心链路（Cookie 解密 → 令牌换取 → 内部 RPC）已经打通且有相当细致的逆向注释与容错设计，真正的问题集中在**状态边界**（谁拥有 Cookie 文件、进程/线程之间如何共享）与**静默失败**（出错时不报错、返回空、或悄悄降级）两处。

三条主线：

1. **凭证被多处独立持有，且没有任何一方负责持久化**。
   `GeminiWebClient` 在请求链路里轮换 `__Secure-1PSIDTS`，但没有持久化回调；只有 `server.py` 的后台线程会把 cookie 写回文件。结果是：进程重启可能拿着已被服务端吊销的旧 `1PSIDTS`；写回是"直接截断 + 事后 chmod"，非原子；多个进程共用同一个 `cookies.json` 会互相拆台。
2. **错误路径上有大量"静默"分支**。
   空流/半流不报错（返回 `text=""` 且 `completed=False` 也算成功）、`FrameParser` 一旦失步就永久卡死并静默吞掉后续所有帧、`batchexecute` 失败返回空列表、macOS 密钥获取失败被完全吞掉。上层 Agent 看到的是"模型没回答"，而不是"连接坏了"。
3. **超时与重试预算没有总上限**。
   `timeout` 实际是单次 socket 读间隔；叠加会话自愈（`rotate + init`）、2 次瞬态重试、4 档模型降级链，最坏情况一次 `generate()` 可阻塞到接近一小时，远超 MCP 侧 `toolCallTimeoutMs=600000`。

**最该先修的 5 条（本地 agent 复核后的排序）**：

| # | 问题 | 为什么最优先 |
|---|---|---|
| 1 | Cookie 轮换不落盘 + 写回非原子 | 唯一会**直接导致服务不可用**的缺陷，且是 10~45 行的局部改动 |
| 2 | 全量 Cookie 明文落盘 + 固定路径 + 本机绝对路径入库 | 唯一会**直接泄漏账号凭证**的缺陷，改动几乎零成本 |
| 3 | 流式响应无完整性校验（空流当成功） | 把"故障"伪装成"模型没话说"，Agent 会基于空结果继续推理 |
| 4 | HTTP 400 被当会话过期，且 `init` 与 `_heal_session` 嵌套双轮换 | 小故障被放大成强制轮换风暴，触发 Google 侧风控 |
| 5 | `FrameParser` 失步即卡死 + 无界帧累积 | 长思考/长回答场景下既丢内容又涨内存，且现象极难归因 |

> 与 Gemini 原始排序的差异：Gemini 把"全局单例跨线程"列为 P0（本文档保留 P0 定级，但推到迭代二）。
> 理由是它需要先做结构性改造（锁边界 + 每线程 session），属于"会崩溃但不常见"（stdio 单进程单线程下几乎不触发），
> 而 1/2/3/4 是"已经在线发生或一次触发就瘫痪"。定级不变、顺序后移。

### P0-1 请求链路轮换的 Cookie 未持久化，且写回非原子

- **严重度**：P0｜**成本**：S（约 45 行）｜**出处**：Gemini A#1、C#1
- **证据**
  - `gemini_client.py:529-546`（`init`）、`623-627`（`ensure_fresh`）、`646-665`（`_heal_session`）都会调用 `self.rotate_cookies()`，但 `GeminiWebClient` **没有任何持久化回调**：
    ```python
    def ensure_fresh(self, force: bool = False) -> None:
        if force or time.time() - self._last_rotate_at >= 1500:  # every ~25 min
            self.rotate_cookies()
    ```
  - 唯一写回点在 `server.py:157-187` `_persist_cookies`，且由后台线程 `server.py:190-199` 调用：
    ```python
    Path(path).write_text(
        json.dumps(entries, ensure_ascii=False, indent=2), encoding="utf-8"
    )
    os.chmod(path, 0o600)
    ```
- **后果**
  1. **重启即失效**：常驻服务在某次请求中轮换了 `1PSIDTS`（内存已新、磁盘仍旧），若在后台线程下次唤醒（最长 25 分钟）前重启，磁盘上的旧令牌已被服务端吊销 → 重启后鉴权失败（推测链，但两道防线都成立）。
  2. **非原子写**：`write_text` 直接截断原文件；写入中途被杀或多实例并发，`cookies.json` 可能变成半截非法 JSON → 下次 `_load_cookies()` 直接失败、服务瘫痪。
  3. **权限窗口**：先创建/截断文件、后才 `chmod`，中间存在 `0644` 窗口；且 Windows 上 `os.chmod` 基本是空操作，等同永远没有收紧权限。
  4. **多进程互斥缺失**：两个进程共用同一 `cookies.json` 时，A 的轮换会让 B 内存里的令牌失效，而 B 不会在 heal 前重读磁盘，反而拿旧凭证再打一次 `RotateCookies`。
- **建议改法**
  1. `GeminiWebClient.__init__` 增加 `on_cookies_rotated: Optional[Callable[["GeminiWebClient"], None]] = None`，`rotate_cookies()` 成功后统一回调；MCP 侧把它接到 `_persist_cookies`（约 10 行）。
  2. `_persist_cookies` 改原子写：`tempfile.mkstemp(dir=同目录)` → `os.fchmod(fd, 0o600)` → `json.dump` → `flush` + `os.fsync` → `os.replace`（约 35 行，可参考 A#1 给出的骨架）。
  3. `_heal_session` 轮换前先比较磁盘 `cookies.json` 的 `mtime`：磁盘更新则先重载进内存 jar，再决定是否需要轮换（跨进程防拆台）。
  4. Windows 上权限另走 ACL（或至少把 cookie 文件放到 `%LOCALAPPDATA%` 并对目录用 `icacls` 收紧）。
- **本地核对（含实测证据）**：A#1 说 `_persist_cookies` 在 `172-182` 行、`os.chmod` 紧跟在写入后 —— 与实际 `181-184` 行一致，方向正确。
  本地实跑 `pytest -q` 结果为 **1 failed / 62 passed**，唯一失败用例是 `tests/test_gemini_client.py::test_persist_cookies_writes_file`，
  失败断言正是 `tests/test_gemini_client.py:663` 的 `(cookie_file.stat().st_mode & 0o777) == 0o600`。
  即：**Windows 上 `os.chmod(path, 0o600)` 根本不生效**，这条本应是"P0 凭证保护"的测试在 Windows 上从未真正通过（该失败在本次评审前已存在，非评审造成）。
  另外本地确认：`_persist_cookies` 写的是 `[{name,value,domain,path}]` 列表，而 `tools/*` 系列工具写的是 `{name: value}` 字典，两种格式并存（见 P2-3）。

### P0-2 全量 Cookie 明文落盘：固定路径、`0600` 仅在事后、仓库内含本机路径

- **严重度**：P0｜**成本**：S｜**出处**：Gemini C#1、C#2、B#5
- **证据**
  - `README.md:44-50` 要求"全量导出、一个不落"，默认落到 `~/.config/gemini-web-mcp/cookies.json`；`README.md:52` 示例用相对路径 `--cookie-file cookies.json`（就在项目工作目录里）。
  - `README.md:132-134` 说明后台每 25 分钟 `RotateCookies` 换新并**写回 cookie 文件**。
  - `server.py:184` 的 `os.chmod(path, 0o600)` 在写入之后，Windows 上还不生效。
  - `tools/mcp-browser-profile.ps1:48-56` 会先把 cookie 落到仓库内 `.cache/cookies-cdp.json` 再拷贝到目标路径。
  - `tools/refresh_cookies.py:22`、`cordis.patch.yml:30-35` 内置了**开发者本机绝对路径**（含 Windows 用户名、uv 安装目录、本地代理端口），属于已入库的路径/身份泄漏（细节见 P1-2，本文档不复制原值）。
- **后果**：一次 `git add .` 就可能把明文 Google 会话（`__Secure-1PSID`/`1PSIDTS`/`SAPISID`）推进公开仓库；同机任意低权限进程可按固定路径直接读走整段会话；崩溃转储/终端回滚里也会留痕。
- **建议改法**
  1. **最小化落盘**：只保留 `{"__Secure-1PSID", "__Secure-1PSIDTS", "__Secure-1PSIDCC"}` 等必需项，其余（追踪类、跨站类）加载后即丢，写回时不写。
  2. **原子 + 权限**：`dir mode 0700` + `file 0600`（POSIX），Windows 走 `icacls`；创建时即收紧，不留窗口。
  3. **`--reveal` 强制掩码**：只输出前 4 位 + `<REDACTED>`。
  4. **默认路径不放项目目录**：`server.py` 启动时若 `GEMINI_COOKIE_FILE` 指向 `cwd`/仓库路径，打印明确告警（本地 agent 补充的迂回检查，成本 S）。
  5. `.gitignore` 已有 `cookies*.json` / `*_cookies.json`（**这条 Gemini 建议的基线已满足**），需补 `*cookie*.json`、`.env`、`*.cookies`。
- **本地核对**：`git ls-files` 已验证当前仓库**没有**跟踪任何 cookie 文件；但仍需按 checklist 复查历史提交。
  另有一项**本地 agent 补充发现**（Gemini 未看到工作区）：仓库 `.cache/` 下现存多份明文凭证残留 —— `.cache/cookies.json`、`.cache/cookies.json.bak-*`、`.cache/cookies-cdp.json`、`.cache/resilience/cookies_*.json` 等，均被 `.gitignore` 的 `.cache/` 覆盖（不会入库），但属于"磁盘上长期明文躺着账号会话"，建议随迭代一第 9 项一并清理（删除或迁出仓库目录）。

### P0-3 流式响应无完整性校验，"空流"被当成功

- **严重度**：P0｜**成本**：M（约 50 行）｜**出处**：Gemini A#3
- **证据**
  - `gemini_client.py:897-950` `_consume_frame` 只检查一条固定错误码路径 `[5, 2, 0, 1, 0]`；`gemini_client.py:797-845` `_stream_once` 在流结束后**不校验 `result.completed`、不校验文本是否为空**：
    ```python
    inner_str = get_nested(frame, [2])
    if not isinstance(inner_str, str):
        return
    ```
  - `gemini_client.py:1153-1177` `_batch_execute_once` 同样不看帧内错误码，失败时返回空列表。
  - 重放风险：`_run_with_resilience`（`667-713`）在中途断流时**原样重放**同一 `metadata`，而服务端可能已经落库了这一轮。
- **后果**：Google 改一个槽位、返回空流、或流在首个 candidate 前被正常关闭（HTTP 200），调用方都会拿到 `{text: "", completed: false}` 的"成功"结果；上层 Agent 无法区分"模型拒绝回答"和"链路坏了"。中途断流重放则可能在会话里插入重复提问，或撞上 `1050` 模型冲突。
- **建议改法**
  1. `_stream_once` 收尾校验：`if not result.completed and not result.text and not result.media: raise GeminiWebError(..., transport=True)`（约 6 行，立刻消掉最恶劣的静默路径）。
  2. `_consume_frame` 增加"候选为空但帧非空"的诊断日志（含帧序号与顶层长度，**不含正文**）。
  3. 记录是否已拿到 `conversation_id`/`response_id`；重试前用 `read_conversation` 确认最新一轮是否已落库，避免盲目重放（约 20 行）。
  4. `_batch_execute_once` 加帧级错误码检查。

### P0-4 HTTP 400 被判为会话过期；`init` 与 `_heal_session` 嵌套双轮换

- **严重度**：P1｜**成本**：S（约 35 行）｜**出处**：Gemini A#5
- **证据**
  - `gemini_client.py:175`：`SESSION_HEAL_STATUSES = frozenset({400, 401, 403})`
  - `gemini_client.py:646-665` `_heal_session` 先 `rotate_cookies(force=True)` 再 `init(force=True)`；而 `init`（`529-546`）在 `_fetch_tokens` 失败时**又**会 `rotate_cookies(force=True)` —— 一次 heal 可在毫秒级连打 2 次 `RotateCookies`，绕过 `rotate_cookies` 里的 60s 冷却（`580-614`）。
- **后果**：参数类 400（坏 `metadata`、不支持的文件类型）被当会话过期 → 白烧一次 `RotateCookies` + 一次 `GET /app` + 原样重放；真故障时 4 档降级链累计可达 8 次强制轮换，触发 Google 侧限流/风控（推测）。
- **建议改法**
  1. `init(force=True, allow_rotate=False)`：heal 链路里只抓令牌，不再自己轮换。
  2. `rotate_cookies` 加硬最小间隔（即便 `force=True`，距上次请求 < 10s 直接返回）。
  3. `SESSION_HEAL_STATUSES` 收窄为 `{401, 403}`；400 只有响应体含 session/token 失效特征时才 heal。
  4. `healed` 标志上提到 `generate()` 级别：一次 `generate()` 跨降级链最多 heal 一次。

### P0-5 `FrameParser` 失步即永久卡死；帧累积无界；`decode_unicode` 编码陷阱

- **严重度**：P1｜**成本**：S（约 35 行）｜**出处**：Gemini A#4
- **证据**
  - `gemini_client.py:387-441` `FrameParser.feed`：
    ```python
    m = re.match(r"(\d+)\n", self._buf[pos:])
    if not m:
        break
    ```
    非数字/非完整长度头一律 `break`，且 `pos` 不前进 —— 之后所有 chunk 只会堆到 `self._buf` 尾部，**整条流剩余数据永久丢弃**（含最终回答与 `completed`）。
  - `self._buf` / `parser.frames`（`435`）/ `result.raw_frames`（`835`）三处无界累积；服务端每帧携带的是累积文本快照，长回答下内存呈平方级增长。
  - `_stream_once` 用 `iter_content(..., decode_unicode=True)`（`828`）依赖 `resp.encoding`；若响应头缺 charset，`chunk` 会是 `bytes`，`self._buf += chunk` 直接 `TypeError`。
- **后果**：一次前缀分块、一个长度偏差、一个异常帧，就让整条回答"静默消失"；长思考回答内存暴涨；缺 charset 时以 `TypeError` 形式炸掉，错误信息完全不指向根因。
- **建议改法**
  1. 显式 `if not resp.encoding: resp.encoding = "utf-8"`，或改用 `codecs.getincrementaldecoder("utf-8")` 手工解码。
  2. 解析器区分三类：完整头 → 正常解析；纯数字尾巴（半包）→ 等待；其它 → **重同步**到下一个 `\n<digits>\n` 边界并记 warning（不要 `break`）。
  3. `raw_frames` 默认不收集，仅 `keep_raw_frames=True` 时收集；删除 `parser.frames` 累积列表。
  4. 加单帧长度上限（如 32MB）防恶意/损坏长度头撑爆内存。

### P0-6 超时/重试/降级没有总预算

- **严重度**：P0｜**成本**：M（约 25 行）｜**出处**：Gemini A#3
- **证据**：`gemini_client.py:814` 把 `timeout=self.timeout` 直接传给 `session.post(..., stream=True)`（`requests` 只约束相邻 chunk 的读间隔）；叠加 `_run_with_resilience` 的 2 次重试、`model_chain` 的 4 档降级、以及每档可触发的会话自愈（`rotate` + `init`），最坏组合可达数千秒。
- **后果**：远超 MCP 的 `toolCallTimeoutMs=600000`（README:80），调用方超时放弃但服务端仍在跑，下一次调用又排队，形成雪崩式堆积。
- **建议改法**
  1. `timeout` 拆成 `(connect_timeout, read_timeout)`，例如 `(15, 60)`。
  2. `generate()` 入口算一个 `deadline = monotonic() + budget`（建议 300s，可由 `GEMINI_TIMEOUT_BUDGET` 覆盖），每档降级/每次重试前检查，超预算直接失败并给出清晰错误（不静默降级）。
  3. 把"已耗时/剩余预算/当前档位"写进错误消息，便于上层决定重试。

### P1-1 全局单例 `GeminiWebClient` 跨线程共享 `requests.Session`，可变态被污染，缓存无界

- **严重度**：P0（定级）/ 迭代二优先｜**成本**：M（约 60 行）｜**出处**：Gemini A#2
- **证据**
  - `server.py:46-51`：`_client` 全局单例 + `_metadata_cache` 无上限字典；`server.py:190-199` 后台线程与工具调用并发使用同一 `_client`。
  - `server.py:344-345`：`if language and language != client.language: client.language = language` —— 单次调用永久改写全局语言。
  - `gemini_client.py:510-516`：`requests.Session()`、`self.access_token`、`self._reqid` 均无锁。
- **后果**：后台轮换线程遍历 `session.cookies` 与主线程收 `Set-Cookie` 并发时可能 `RuntimeError: dictionary changed size during iteration`；`language` 串味；`_metadata_cache` 常驻泄漏；进程重启后 `candidate_id` 等槽位丢失导致续聊上下文断裂（推测）。
- **建议改法**
  1. 客户端内加 `threading.RLock()`，覆盖 `init`/`rotate_cookies`/`get_cookie`/`_next_reqid`/快照导出；或每线程一个 `Session`、只共享受锁保护的状态。
  2. `language` 改成 `generate(..., language=None)` 的单次参数。
  3. `_metadata_cache` 换 `OrderedDict` LRU（上限 512），miss 时用 `read_conversation` 回填。
- **本地核对**：stdio 单进程 + 单请求串行的典型用法下几乎不触发，所以它排在 P0-1…P0-6 之后；但 `--transport http` 或未来并发调用会放大，定级维持 P0。

### P1-2 硬编码开发者本机绝对路径（含用户名、uv 路径、本地代理端口）

- **严重度**：P1｜**成本**：S｜**出处**：Gemini B#5、C#2
- **证据**
  - `tools/refresh_cookies.py:22-23`：`PROFILE` 写死开发者本机 Cherry Studio 绝对路径（含 Windows 用户名），且 `--out` 仍会无条件创建默认目录（`61-64`）。
  - `cordis.patch.yml:30-35`：`command` / `cwd` / `GEMINI_COOKIE_FILE` 的默认值均为开发者本机绝对路径（含用户名），并把 `HTTPS_PROXY`/`HTTP_PROXY` 默认钉死到本地 `127.0.0.1:7877`。
  - `tools/refresh-cherry-cookies.ps1:15` 与 `tools/mcp-browser-profile.ps1:14` 同样带本机绝对路径默认值。
- **后果**：任何公开分发后，访客/下游用户可直接读出用户名与目录结构；下游未设环境变量时会尝试执行别人机器上的路径 → 子进程启动失败并把该路径写进下游日志；代理默认值会让"别人的 7877 端口"接管发往 Google 的流量（若该端口被占用）。
- **建议改法**
  1. `cordis.patch.yml` 默认值改为通用回退（`'uv'`、`process.cwd()`、空串），代理默认置空、仅由用户环境提供。
  2. `refresh_cookies.py` 按平台推导 Cherry Studio 路径，新增 `--profile-dir` / `GEMINI_CHERRY_PROFILE` 覆盖；删掉多余的 `TARGET.parent.mkdir`。
  3. 加提交前扫描（CI / pre-commit）正则拦截 `[A-Za-z]:[\\/]Users[\\/]<name>` 与 `/Users|/home/<name>`。
  4. 若这些文件已进过公开历史，按 checklist 用 `git filter-repo` 清理（本地 agent 核对：当前工作区 `git ls-files` 显示 `refresh_cookies.py`、`refresh-cherry-cookies.ps1` 已被跟踪，**需确认远端历史**）。

### P1-3 CLI / 库 / MCP 边界混杂

- **严重度**：P1｜**成本**：S｜**出处**：Gemini B#3
- **证据**
  - `cookie_extractor.py:434-469` `main`：`WARN:` 与提示都打到 **stdout**；未传 `--list`/`--reveal` 时仍打印全部 cookie（值已掩码）。
  - `tools/refresh_cookies.py:26-34`：库函数里 `raise SystemExit(...)` —— 被任何宿主 import 调用都会直接终结宿主进程。
  - 退出码三套语义：`cookie_extractor` 只要拿到任意 cookie 就 `0`；`refresh_cookies.main` 永远 `0`；`dump_cookies_cdp.mjs` 缺关键 cookie 时 `2`、异常 `1`。
- **后果**：MCP stdio 依赖纯净 stdout，任何 `WARN`/提示都会污染 JSON-RPC 帧（虽然该 CLI 不与 stdio 复用，但同一套代码被当作 driver 调用时就是隐患）；外部脚本无法用退出码判断刷新成败。
- **建议改法**
  1. 库层定义 `CookieExtractionError`，`SystemExit` 改异常，只在 CLI `main()` 顶层转退出码。
  2. 统一退出码：`0` 成功且含关键 cookie｜`1` 运行/I/O 失败｜`2` 拿到 cookie 但缺关键字段｜`3` 参数非法。
  3. 全部诊断走 `stderr`；新增 `--json`，stdout 只出合法 JSON。

### P1-4 非交互场景缺阻塞控制

- **严重度**：P1｜**成本**：S｜**出处**：Gemini B#4
- **证据**
  - `cookie_extractor.py:216-231`：macOS 直接 `subprocess.run(["security", ...])`，裸 `except Exception: return None`；`extract_cookies:364` 又用 `if not key and _platform_key() != "darwin"` 把 macOS 的错误信息整体吞掉 → 无头环境下每次调用硬阻塞 15 秒且**零诊断**。
  - `cookie_extractor.py:375-379`：只 `except sqlite3.Error`；而 `_read_cookie_rows`（`306-323`）里 `shutil.copy2` 在浏览器运行时抛的是 `PermissionError`（`OSError`），直接以堆栈崩溃。
  - `tools/dump_cookies_cdp.mjs:17-42`：`fetch` 与 `WebSocket` 均无超时，也没有 `error`/`close` 监听 → 连接失败时 Promise 永不 settle，Node 进程挂死。
- **建议改法**：macOS 返回 `(key, error_reason)` 并去掉 `darwin` 特判、非 TTY 时超时缩到 3s；`except (sqlite3.Error, OSError)` 并给出"数据库被浏览器占用，请关闭浏览器或用 CDP"的明确提示；CDP 脚本用 `AbortSignal.timeout` + `ws` 的 `error`/`open` 竞速（约 15 行）。

### P1-5 诊断/日志/错误消息可能把凭证与路径带进 Agent 上下文

- **严重度**：P1｜**成本**：S｜**出处**：Gemini C#3
- **证据**：`server.py:255-302` `gemini_status` 返回 `cookie_count` / `cookies_present` / `errors`；`server.py:678-681` 日志格式无脱敏；`server.py:707-711` HTTP 模式把自动生成的 Bearer token 明文打到 stdout；异常路径里有 `resp.text[:200]`（`gemini_client.py:1064`、`1070`）与完整本地路径（`1029`）。
- **本地核对（重要修正）**：Gemini 认为 `gemini_status` 会返回 cookie 键值 —— **代码事实是不会**（只返回名字与计数，见 `261-272`）。另外 Gemini 说 HTTP 模式"未显式约束绑定地址" —— **也不成立**，`server.py:712` 明确 `_run_http_async("127.0.0.1", ...)`。
  因此本条的真实风险是**趋势性/潜在**的：一旦有人为了排障把 `errors` 或响应片段塞进返回体，就会直接把凭证/路径送进云端模型上下文与聊天记录。**定级从 Critical 降为 P1**。
- **建议改法**
  1. 日志/异常统一脱敏 filter（正则覆盖 `__Secure-1PSID*`、`SAPISID`、`APISID`、`SNlM0e`、`Bearer <token>`）。
  2. 对外错误只用错误码 + 人话（`{"error_code": "AUTH_SESSION_EXPIRED", ...}`），不 `str(exc)` 透传。
  3. `gemini_status` 返回值字段白名单化（布尔 + 时间戳），永不返回 cookie 值、令牌、cookie 文件路径。
  4. HTTP token 改由环境变量注入或写 0600 文件，不打印到 stdout。

## 四、明确不做的项及理由

| 不做的事 | 理由 |
|---|---|
| 迁移到官方 Gemini API | 项目存在的前提就是"免 API Key、不产生 API 计费、复用网页端额度"；迁移等于把项目重写成另一个东西。 |
| 引入 `pydantic-settings` / 独立配置文件（`.env`、`config.toml`） | MCP 宿主的标准配置通道就是 `env` 字段；再加一层配置会制造"宿主 env vs 本地文件"的双真相源。标准库 `dataclasses` + `os.environ` 足够（Gemini 结论一致）。 |
| 引入 Playwright / Selenium 做浏览器自动化 | 与"轻量逆向客户端"定位冲突（体积、启动时间、维护成本）；v20 app-bound 场景已由 CDP 脚本覆盖，只需补超时。 |
| 多账号池 / 额度轮换 / 代理池 | 明显加剧 ToS 违规与封号面，且项目定位是个人小号工具；不做。 |
| 全量重写为 `asyncio`/`aiohttp` | 收益主要在并发，而 MCP 工具本身是同步函数；先修锁与预算问题即可，重写风险远大于收益。 |
| 本轮做 Cookie 加密存储（DPAPI/Keychain 封装） | 方向正确但涉及三平台实现与迁移，收益可被"最小化落盘 + 0600 + 原子写"覆盖 80%；留待迭代三后单独评估。 |
| 做 `deep think`（thinking=3）异步轮询编排 | 网页端首帧只回占位、行为不稳定；`extended(2)` 已满足日常需求，维护成本不值。 |
| 自动发现 `build label` / 动态 RPC id 探测 | 过度工程：现有常量 + 报错已足够，探测逻辑本身会成为新的故障点。 |
| 重命名包（`gemini-web-mcp` ↔ `Gemini-Eyes`） | 会破坏 DSH bundle、`uv` 脚本入口与用户既有配置，收益仅为命名一致性；不做。 |
| 补齐完整 i18n / 多语言文档 | 非本轮目标；README 的英文注释已够。 |
